## 3. 아직 결정 안 된 4가지 쟁점

### 쟁점 1 — 마이데이터 사업자 vs 마이데이터 활용 서비스 (2026-08-19 수정)

> **[08.19 갱신] MVP 스코프 변경**: 이 서비스는 **마이데이터 연동으로 확보한 과거 소비 기록 + 사용자가 직접 입력하는 미래 변화 지출값**을 함께 바탕으로 카드(조합)를 추천하는 서비스로 확정되었습니다. 기존 판단("MVP는 라이선스·제휴 없이 사용자 직접 입력만으로 시작")은 폐기합니다 — F-01(미래지출 입력)은 그대로 사용자 직접 입력이지만, F-02(보유카드/제약조건 파악)는 마이데이터 연동을 전제로 합니다.

| | 내용 |
| --- | --- |
| 질문 | 우리가 마이데이터 사업자(직접 인가)가 될지, 뱅크샐러드·토스처럼 마이데이터를 "활용"하는 입장일지 |
| 확인된 사실 🔵 | 뱅크샐러드·토스 모두 실제로는 금융위 마이데이터(본인신용정보관리업) 인가를 **직접 보유**한 사업자임. 특히 토스는 은행·증권·PG업까지 겸영하는 대형 금융그룹이라 "가벼운 제3자 서비스" 비유 대상으로 적절하지 않음 |
| 판단 (08.19 수정) | MVP부터 **마이데이터 연동으로 과거 소비 기록을 확보**하고, 여기에 사용자가 입력하는 미래 변화 지출값을 더해 카드 조합을 계산·추천. 뱅크샐러드·토스처럼 직접 인가를 새로 딸지, 기존 인가 사업자와 제휴할지는 **더 이상 미룰 수 없는 결정** — 32시간 컨설팅 프로젝트 스코프상 실제 인가 취득은 비현실적이므로, 제휴(예: 기존 마이데이터 사업자의 API 활용) 전제를 기본 가정으로 두고 강사에게 확인 필요(아래 🟡) |
| 미해결 리스크 🟡 | (1) 인가 vs 제휴 경로 미확정 — 팀 논의 필요. (2) 마이데이터 API 접근 자체가 전제 조건이 되면서, `0818_서비스 기초 컨설팅 점검.md` 항목 6("마이데이터 API 전제 없이 직접입력으로 우회 가능")의 결론이 더 이상 유효하지 않음 — 재검토 필요 |

### 쟁점 3 — TAM-SAM-SOM 시장 세그먼트 (2026-08-19 재분석, 3차 수정)

> 최초 "투트랙 구조"(SAM=이벤트로 좁힘, SOM=이벤트 무관 확장)는 SAM보다 SOM이 더 넓어지는 역전 구조라 표준 TAM⊇SAM⊇SOM 포함관계와 맞지 않았습니다. 08.18 1차 재분석에서 SAM=이벤트 무관 전체/SOM=혼인 Beachhead로 포함관계를 바로잡았고, 08.18 2차 재분석에서는 효진의 지적(쟁점 1의 MVP는 마이데이터 미연동인데 "TAM=마이데이터 가입자"는 이와 모순)을 반영해 TAM을 "국내 신용카드 실사용자 전체"로 교정했습니다. 그러나 같은 날 추가 논의(`0818_TAM 정의 재논의 정리.md`)에서 두 가지 반박이 나왔습니다 — ① 신용카드 실사용자는 자격은 있지만 채택 가능성은 낮은 사람을 너무 많이 포함해 시장 규모가 실제 타겟과 동떨어져 보임, ② "신용카드 사용자"는 사실상 성인 대부분이라 필터링 기능이 거의 없고 디지털 비친화 인구까지 섞여 들어감. **08.19 팀은 이 두 반박을 근거로 TAM을 다시 마이데이터 이용자로 되돌리기로 확정했습니다(옵션 A).**
>
> **[08.19 추가 갱신] 쟁점 1 정정으로 모순 해소**: 아래 3차 수정 직후에는 이 TAM 재확정이 효진의 원래 지적(마이데이터 가입 여부는 우리 제품 자격 조건이 아니라는 지적)을 "해소가 아니라 감수"하는 것으로 처리했었습니다. 그러나 같은 날 팀이 쟁점 1 자체를 정정해 **MVP부터 마이데이터 연동을 포함**시키기로 하면서(위 쟁점 1 참고), 이 모순은 실제로 해소되었습니다 — 마이데이터 이용자는 이제 "채택 가능성 앵커"가 아니라 **문자 그대로 우리 제품을 쓸 수 있는 실제 자격 기준**입니다. TAM을 굳이 재정의·우회할 필요가 없어졌습니다. 표기: 🔵 Fact(확인) · ⚪ Inference(추정) · 🟡 Assumption(가정) · 🟠 미확보 — `방법론.md` 8장 기준.

**변경 이력**: (1차, 08.18) SAM⊃SOM 포함관계 교정 → (2차, 08.18) TAM 앵커를 마이데이터 가입자에서 신용카드 실사용자로 교정 + SOM 채택률의 근거 없는 확정 인원수 표기 제거 → (3차, 08.19) 신용카드 실사용자 앵커가 채택 가능성 낮은 인구·디지털 비친화 인구까지 과다포함한다는 반박을 근거로 TAM을 다시 마이데이터 이용자로 되돌림(옵션 A), 당초에는 쟁점 1과의 모순을 감수하는 것으로 처리 → (4차, 08.19 같은 날) 쟁점 1 자체를 "MVP부터 마이데이터 연동 포함"으로 정정하면서 모순이 실제로 해소됨 — TAM=마이데이터 이용자가 이제 문자 그대로의 자격 기준.

**혼인(Q1) 지출강도 근거**: 결혼비용 총계 5,912만원(주택자금 제외, 🔵 듀오 2026) 중 카드결제 확실 항목(신혼여행 1,030만원+혼수 1,445만원+웨딩패키지 471만원=2,946만원, 1인당 1,473만원)과 조건부 포함 시(+예식홀 1,460만원, 1인당 2,203만원)로 구분. 예단·예물(1인당 675.5만원)은 현금 관행이 강해 카드결제 대상에서 제외.

**판단**: 제품 로직(F-01~F-06)은 이벤트 비종속으로 유지(쟁점 2). TAM-SAM-SOM의 실제 확정 수치는 `효진/TAM-SAM-SOM 정의 작업안.md`의 7단계 절차(KOSIS 원자료 수집 → 대리지표 중복 제거 → 보수/기본/공격 3시나리오 민감도)를 따라 채웁니다 — 이 문서(쟁점정리)는 그 절차의 **정의·구조**만 확정한 것이며, 실수치는 아직 확정이 아닙니다. 중복 작업을 피하기 위해 실수치 수집은 효진의 절차서를 따르는 것을 권장합니다.

**한계 및 검증 필요 항목**:
- TAM 고유인원 수는 추정치 — 마이데이터 가입 건수(1.77억 건, 중복포함)를 고유인원(약 3,000만 명)으로 환산하는 방식 자체가 미확정, 서비스별 중복가입 제거 필요(효진 절차서 §2-1 갱신 예정)

- SOM의 Beachhead 비중·채널 도달률·Payment Plan Selection Rate 3개 변수 모두 미확정 — Concierge Test(피치덱 9장) 실측 전까지 확정 인원수로 제시 금지

- 혼인 지출 항목별 실제 카드결제 비율(🟡 표기 항목)은 관행 추론이며 1차 통계 미확인

### 쟁점 4 — 카드 구성 재설계: 몇 장을 남기고 몇 장을 더할까 (2026-08-19 재정의)

> 기존 판단은 "기존 카드만 쓰는 안"과 "신규카드 1장을 추가하는 안", 이 둘만 계산해 나란히 비교하면 된다고 봤습니다. 그런데 실제로는 사용자가 "카드가 5장이라 연회비가 아까우니 몇 장으로 줄이고 싶다"거나 "카드가 1장뿐인데 가족이 늘어서 지출이 커질 것 같으니 몇 장을 더 만드는 게 좋을지 보고 싶다"고 말할 수 있습니다. 두 경우 모두 F-04~F-06이 원래 다루기로 한 문제(보유·신규카드 조합을 계산 근거와 함께 재배치)에 정확히 들어맞는데, "신규카드는 최대 1장까지만"이라는 숫자 제한 때문에 다루지 못하고 있었습니다.

| | 내용 |
| --- | --- |
| 질문 | 카드 조합을 다시 짤 때, 몇 장을 해지하고 몇 장을 새로 추가할 수 있게 할 것인가? 그리고 그 결과를 사용자에게 어떻게 보여줄 것인가? |
| 기존 판단(폐기) | 신규카드는 최대 1장까지만 비교 — "기존 카드만 쓰는 안" vs "기존+신규 1장 추가하는 안", 이 두 안을 나란히 보여주고 사용자가 고르게 함 |
| 새 판단 (08.19 2차 갱신) | 신규카드 수를 1장으로 못박지 않고, 해지·유지·신규추가를 몇 장이든 함께 계산한다. **다만 결과는 "안 A/안 B" 식으로 나열해서 비교시키지 않고, 계산으로 압축된 하나의 최적 조합만 결론으로 제시한다** — 예: "A·B카드 해지, C카드 유지, D카드 신규 추가". 지금 그대로 두는 것보다 나은 조합이 없으면 결론은 "유지"가 된다(`윤정/0819_메커니즘_전이_분석표.md` §2-4 게이팅 원칙을 다중카드로 확장 적용) |
| 계산이 크게 복잡해지지 않는 이유 | "몇 장을 줄일까"는 이미 계산 중인 각 카드의 순혜택이 그 카드의 연회비보다 낮은지만 보면 되므로 새로운 계산 로직이 필요 없습니다. "몇 장을 늘릴까"도 신규카드 후보군을 트렌드별 대표 카드 소수(5~10종 정도)로 제한해두면, 보유카드와 후보군을 합쳐 계산해도 부담이 크게 늘지 않습니다. 결과를 하나로 압축하는 것도 "여러 안을 다 계산해서 보여주기"보다 오히려 계산량이 줄어드는 방향입니다 |
| 유의점 ⚠️ | Guardrail G-04(불필요한 신규카드 추천 방지)·G-05(카드 수 통제)는 그대로 유지합니다. 결론은 하나뿐이지만, 그 결론이 왜 맞는지는 "지금 그대로 두면 얼마를 놓치는지"와 "계산 근거"를 함께 공개해서 보여줍니다(차별점 C, `0819_03_KSF 분석.md` §3) — 결과를 하나로 줄인 것이 근거 공개를 줄이는 것은 아닙니다 |
