## 1. 뱅크샐러드 — 보유카드 기준 대체카드 탐색·비교

| 구분 | 분석 항목 | 상세 내용 |
| :--- | :--- | :--- |
| **1. 원본 분석** | **표면적 기능 (Feature)** | 보유카드 실적·혜택을 마이데이터 소비내역에 대입해, 동일 소비 패턴 기준 더 높은 예상 혜택을 주는 대체 카드를 자동 탐색·비교 리스트로 제시 (예: "지난달 소비 패턴이면 B카드로 월 12,000원 더 받을 수 있어요") |
| | **핵심 메커니즘 (Mechanism)** | 사용자의 **실제 과거 행동 데이터**를 준거점(reference point)으로 고정 → 현재 상태(보유카드)와 대안(대체카드)의 차이를 금액으로 정량화 → "지금 선택이 만들어내고 있는 기회비용"을 가시화 |
| | **작동 심리/경제학적 원리** | 손실 회피(Loss Aversion) · 기회비용의 가시화(salience) · 자기 관련성 효과(self-relevance) · 앵커링(현재 카드가 앵커) |
| **2. 전이 설계** | **전이 가설 (Hypothesis)** | 과거 대신 **미래 예상 지출**(마이데이터 예측 + 사용자 입력)을 기준으로 카드 "조합"을 추천하면, (1) 미래 지출을 입력할 유인 발생(입력해야 손실이 보임) (2) 조합 추천의 설득력 강화 (3) 시나리오 변경 시 재계산 확인을 위한 재방문 유도 |
| | **적용 형태 (Adapted Feature)** | "예상 지출 시나리오 vs 최적 카드조합 갭 비교" — 마이데이터 자동 예측 + 사용자 추가 지출 입력 → 현재 보유 카드조합 vs 최적 조합의 예상 혜택 차액을 손실 프레이밍으로 강조("이 시나리오 기준 +34,000원") → 시나리오 수정 시 실시간 재계산 |
| **3. 검증 & 리스크** | **핵심 검증 지표 (Success Metric)** | 시나리오 입력 완료율, 추천 결과 클릭/전환율, 시나리오 재입력 빈도(재방문), 추천 대비 실제 채택률 |
| | **한계점 및 리스크 (Failure Mode)** | 미래 예측치는 과거 실측보다 불확실성이 커서 손실 프레이밍 신뢰도가 원본보다 희석될 수 있음 · 반복 입력 피로로 인한 이탈 · 카드사 제휴 수익모델과 얽히면 "최적"이 왜곡된 인센티브로 변질 · 넛지 피로 · 카드 조합은 단일 대체보다 실행 복잡도가 높아 "정보만 보고 행동 안 함" 갭 |
| | **보완 장치 (Mitigation)** | 예측치에 근거 뱃지("최근 3개월 평균 기반") 표기 · 마이데이터 자동 추정치를 기본값으로 선제공(입력 마찰 최소화) · 추천 로직을 실적/혜택 기준으로 고정하고 제휴 구조 투명 공개 · 손실 프레이밍 노출 빈도 통제 · "효과 큰 카드 1장부터" 단계적 전환 옵션 |

## 2. 핀트 — Card Portfolio Rebalancing

> **정정 (2026-08-19)**: 핀트는 "상시 모니터링"이 아니라 **분기 등 정기 주기 점검 + 필요 시 알림**이다. 아래 표는 이 정정을 반영했고, 정기 주기 자체는 우리 서비스에 가져오지 않기로 했다(2-1 참고, 이유는 종합 정리 참고) — 가져오는 건 "언제 확인하냐"가 아니라 "바뀔 가치가 있을 때만 개입한다"는 게이팅 로직 하나뿐이다.

| 구분 | 분석 항목 | 상세 내용 |
| :--- | :--- | :--- |
| **1. 원본 분석** | **표면적 기능 (Feature)** | 투자성향·시장상황 기반으로 포트폴리오를 구성·추천하고, 분기 등 정기 주기로 점검해 필요 시 리밸런싱을 제안. 리밸런싱 효익이 거래비용보다 작다고 판단되면 매매를 미룸 |
| | **핵심 메커니즘 (Mechanism)** | 현재 상태(Current)와 목표 상태(Target) 간 괴리(Drift)를 **정기 주기로 점검**하다가, **재구성 비용 대비 효익(Net Benefit)이 임계치를 넘을 때만** 알림·실행을 트리거하는 비용-편익 게이팅. "즉시 반영"도 "무조건 최신화"도 아니라 "정해진 시점에, 바꿀 가치가 있을 때만 개입" |
| | **작동 심리/경제학적 원리** | 거래비용을 고려한 최적정지(optimal stopping) 논리 · 현상유지를 "방치"가 아니라 "판단 후 유지"로 재프레이밍해 신뢰 확보 · Human-in-the-loop 최종 선택권 부여로 통제감(자기결정성) 강화 |
| **2. 전이 설계** | **전이 가설 (Hypothesis)** | 지출 시나리오가 바뀔 때마다 "카드를 바꾸라"고만 하면 넛지 피로·불신을 유발. 핀트의 Net Benefit 게이팅만 이식하고 **정기 주기는 이식하지 않으면**(2-1), "이 지출 변화가 카드 조합을 바꿀 만큼 큰가"를 매번 정직하게 판정할 수 있어 사소한 변화엔 "유지"를 추천해도 신뢰도가 유지된다는 가설 |
| | **적용 형태 (Adapted Feature)** | **Rebalancing Trigger Engine** — 상세 설계는 아래 2-1~2-8 |
| **3. 검증 & 리스크** | **핵심 검증 지표 (Success Metric)** | 트리거 발생률 대비 실제 수용률(제안 채택률), "유지 추천" 메시지에 대한 신뢰도(정성 인터뷰), 재계산 이후 이탈률, 임계치 조정 전후 채택률 변화 |
| | **한계점 및 리스크 (Failure Mode)** | 카드 전환비용(연회비·실적리셋·발급심사)은 투자상품 거래비용보다 정량화가 어려워 Net Benefit 계산 신뢰도가 낮을 수 있음 · "유지하세요"가 반복되면 서비스의 액션 유도 존재 이유가 희석됨 · 반대로 트리거가 너무 잦으면 피로 · 임계치를 잘못 잡으면(너무 낮음) 아슬아슬한 이득으로 전환시켜 실제로는 사용자 손해가 될 수 있음 |
| | **보완 장치 (Mitigation)** | 전환비용을 연회비·실적초기화·발급대기 등 명시적 항목으로 분해해 근거 투명 공개(2-3) · 절대·상대 이중 임계치로 아슬아슬한 제안 필터링(2-4) · 임계치는 하드코딩 시작 → 실사용 데이터로 튜닝(고정 파라미터, 사용자 노출 설정 아님) |

### 2-1. 트리거 조건 — 언제 계산이 도는가

기본값은 **침묵(silent)**: 아무 것도 안 하면 아무 화면도 뜨지 않는다. 캘린더 기반 정기 알림(분기 점검)은 채택하지 않는다 — 우리 서비스에서 Drift가 생기는 원인은 시장이 아니라 **사용자의 입력 행동**이므로, 사용자가 아무것도 입력하지 않으면 애초에 재점검할 게 없다. 계산은 다음 두 이벤트에서만 발생한다.

- **(a) 지출 시나리오 변경** — 사용자가 미래 지출 항목(카테고리·금액·예상 결제월)을 추가/수정/삭제
- **(b) 카드 Rule 변경** — 연회비·혜택율·실적조건이 바뀌어 뱅크샐러드 라인(§1)이 "기존 진단 결과가 stale"이라는 신호를 보낸 경우. 이 신호만 이 엔진에 전달되고, 원인 추적·알림 문구는 §1이 담당

한 세션에서 지출 항목을 여러 개 연속 입력하는 경우(예: 이사 준비로 5개 항목) 항목마다 계산하지 않고 **저장 시점에 1회 배치 계산**한다 — 핀트가 "매매비용을 아끼려 리밸런싱을 미루는" 것과 같은 이유로, 계산 자체는 공짜지만 반복 알림은 사용자에게 피로 비용을 물린다.

### 2-2. Diagnosis — Drift(Gross Gap) 계산식

```
Gross Gap = Σ(신규/변경 지출 항목) [ 최적카드 예상혜택(항목) − 현재카드 예상혜택(항목) ]
예상혜택(항목) = 항목 금액 × 카드의 해당 카테고리 적립률/할인율
              (단, 카드별 월 통합한도·전월실적 구간 충족 여부로 캡핑)
```

### 2-3. Net Benefit 게이팅 — 전환비용 3요소

```
Net Benefit = Gross Gap − 전환비용
전환비용 = a(연회비 차액) + b(실적 재적립 손실) + c(발급 대기 지연비용)
```

- **a. 연회비 차액** — 신규카드 연회비 − 기존카드 연회비(첫해 기준 실제 청구액으로 계산, 반복비용이므로 월할 환산도 병행)
- **b. 실적 재적립 손실** — 이번 결제월에 기존카드가 이미 채워둔 전월실적 구간 진행분 중, 전환 시 사라지는 혜택. 예: 기존카드 실적 30만원 구간에 26만원이 채워진 상태에서 지금 전환하면, 이번 달 4만원을 못 채워 이번 달 혜택 전체를 놓침 → 그 놓친 혜택 금액을 손실로 차감
- **c. 발급 대기 지연비용** — 신규카드 신청→심사→배송까지 걸리는 기간(통상 며칠) 동안은 여전히 기존카드로 결제해야 하므로, 그 기간에 해당하는 지출은 Gross Gap 계산에서 제외(전환 즉시 100% 효과 발생을 가정하지 않음)

### 2-4. 게이팅 임계치 — "유지" vs "제안" 분기 규칙

두 조건을 **모두** 만족해야 "제안"으로 분기하고, 하나라도 미달이면 "유지"로 표시한다.

- **절대 임계치**: Net Benefit ≥ 고정값(예: 월 환산 10,000원) — 이 미만은 반올림 오차·심리적 사소함 수준으로 처리
- **상대 임계치**: Net Benefit ≥ 전환비용 × 배수(예: 1.5배) — "겨우 전환비용을 넘기는" 아슬아슬한 제안을 걸러내, 사용자가 전환 후 오차 범위 내에서 손해로 느끼는 상황을 방지

두 값은 사용자에게 노출하는 설정이 아니라 **서버 측 하드코딩 파라미터**로 시작하고(§2-1에서 언급한 "트리거 민감도 조절 UI"는 폐기 — 지금 단계에서 만들 근거가 없는 과설계였음을 인정), H3·H6 가설 검증 데이터로 사후 튜닝한다.

### 2-5. UX 흐름 (Human-in-the-loop, 토스 라인과 접점)

- **"유지" 결과**: 별도 화면을 띄우지 않거나, 사용자가 진단 화면에 직접 들어갔을 때만 "지금 조합이 최선이에요"로 표시(뱅크샐러드처럼 팝업 강제 노출 금지)
- **"제안" 결과**: 카드 1장 교체안 제시(다중카드 배분은 §3 TMS 보류 상태이므로 범위 밖). 예시 문구: *"여행 지출 40만원, 지금 카드로 쓰면 혜택 0원이지만 B카드로 바꾸면 8,000원 더 받아요 (연회비 3,000원 반영 후)"*
- 자동 발급·자동 결제는 하지 않음 — 사용자가 "적용"을 눌러도 실제 카드 신청은 사용자 책임(MVP Out-of-Scope 유지)

### 2-6. 필요 데이터 — 카드 Rule DB 최소 필드

연회비(국내전용/해외겸용) · 카테고리별 적립률/할인율 및 카테고리 정의 · 전월실적 구간과 구간별 혜택 캡 · 실적 인정 제외 항목(할부·상품권 등) · 월 통합 할인한도 · 신규 발급 프로모션(가입 캐시백 등, 기간 한정) · 평균 발급 소요기간 · 해지 시 위약금/연회비 환급 규정

### 2-7. Edge Case

- 지출 항목을 **삭제**해 시나리오가 줄어드는 경우 → 재계산은 하되, 이미 수락된 과거 전환 제안을 "되돌리기" 하는 로직은 P1으로 미룸(MVP는 신규 진단만)
- 카드 Rule 변경(§2-1의 (b))으로 트리거된 경우, 문구는 "당신의 지출이 바뀌어서"가 아니라 "카드 혜택 조건이 바뀌어서"로 명확히 구분 — 원인을 사용자 탓처럼 보이게 하지 않음

### 2-8. TMS 보류에 따른 스코프

TMS(다중카드 배분, §3)는 보류 상태이므로 이 Rebalancing Trigger는 **지출 항목별로 "가장 유리한 카드 1장"을 각각 추천**하는 수준까지만 구현한다. 카드 수·월예산 등 전역 제약을 걸고 전체를 동시에 최적화하지는 않는다. 오히려 이게 장점 — 다중카드 최적화 없이도 H1(지출 변화가 실제 재검토 트리거가 되는가)·H3(혜택/월부담/간편성 중 실제 우선순위)를 먼저 좁게 검증할 수 있다.

## 3. TMAP TMS — Payment Allocation Optimization

> **상태: 보류 (2026-08-19, 윤정 제안)** — 원본(경로 최적화)과 대상(카드 실적구간 채우기)의 수학적 구조가 다르다는 문제는 여전히 유효하다(아래 표 그대로 보존). 다만 완전 폐기 대신 **보류**로 조정 — §2(핀트)를 먼저 구체화해 MVP를 좁게 검증하고, threshold-filling 재정의가 실제로 필요해지는 시점(다중카드 배분을 다뤄야 할 때)에 재검토한다. 근거는 `decision-log/decision-log.md` 참고.

| 구분 | 분석 항목 | 상세 내용 |
| :--- | :--- | :--- |
| **1. 원본 분석** | **표면적 기능 (Feature)** | 다중 경유지/차량을 대상으로 배송거리·화물량·배송시간 등을 동시에 고려해 배차·경로·도착예정시간을 산출하는 최적화 API |
| | **핵심 메커니즘 (Mechanism)** | 여러 개체(차량)와 여러 목적지(배송지)를 제약조건(적재량·시간창) 하에서 동시에 매칭하는 **다대다 조합 최적화**(assignment/constraint optimization). 부분 최적이 아니라 전체 시스템 관점의 배분을 한 번에 계산 |
| | **작동 심리/경제학적 원리** | 인지부하 위임(delegation of cognitive load) — 사람이 조합을 하나하나 계산할 필요 없이 시스템이 전체를 한 번에 풀어줌 · 복잡성을 숨기고 결과만 제시하는 자동화 신뢰(automation trust) |
| **2. 전이 설계** | **전이 가설 (Hypothesis)** | 여러 개의 미래 지출(냉장고·세탁기·침대 등) × 여러 장의 카드 × 각기 다른 실적/한도/할부조건은 사람이 수동으로 풀기 사실상 불가능한 조합 문제. TMAP TMS의 다대다 배분 최적화를 이식하면 "구매건×카드×시점×할부"라는 4차원 매칭을 시스템이 대신 풀어주는 것이 우리 서비스의 핵심 차별화(단순 카드 1장 추천이 아닌 지출 건별 배분표)가 된다는 가설 |
| | **적용 형태 (Adapted Feature)** | **Payment Allocation Engine**: 입력(미래 구매 목록·보유+후보 카드·카드 Rule[실적/한도/혜택/할부]·제약[월예산/카드수/선호]) → 구매건별 카드·결제시점·할부방식을 배정한 표 형태의 Action Plan 산출. 지출 항목 추가/변경 시 전체 재최적화(재배차와 동일 원리) |
| **3. 검증 & 리스크** | **핵심 검증 지표 (Success Metric)** | 구매건별 배정표의 실제 채택률(추천대로 결제한 비율), 재계산 응답속도 체감, 배정 결과 이해도(정성) |
| | **한계점 및 리스크 (Failure Mode)** | 수학적 최적해가 사용자의 실제 선호(선호 카드, 심리적 애착)와 어긋날 수 있음(Optimization ≠ Preference) · 제약조건을 사용자가 직접 설정해야 하는 진입장벽 · 카드 Rule(실적조건·한도·프로모션)이 자주 바뀌는데 최신화가 안 되면 추천 신뢰도 붕괴(Rule Freshness) |
| | **보완 장치 (Mitigation)** | 최적화 결과를 사용자가 개별 항목 단위로 오버라이드할 수 있게 허용(Human override) · 제약조건 입력을 기본값+선택적 고급설정으로 계층화 · Rule 데이터의 출처·기준일을 항상 표기해 최신성 신뢰 담보 |

## 4. 토스 — Decision UX & Explainability

| 구분 | 분석 항목 | 상세 내용 |
| :--- | :--- | :--- |
| **1. 원본 분석** | **표면적 기능 (Feature)** | TDS 공통 디자인 언어 + 해요체·능동형·긍정 표현의 UX Writing 원칙. 정보를 결론→핵심변화→Trade-off→근거→상세 순으로 계층화해 제시 |
| | **핵심 메커니즘 (Mechanism)** | 복잡한 계산/데이터를 사용자가 즉시 "이해하고 선택"할 수 있는 형태로 압축하는 **정보 위계화**(Progressive Disclosure) + 결과 우선 노출(Result First) + 비교를 통한 의사결정 지원(Compare, Don't Decode) |
| | **작동 심리/경제학적 원리** | 인지부하 이론(cognitive load) — 단계적 공개로 과부하 방지 · 만족화(satisficing) 의사결정 지원 — 최적해를 직접 계산시키지 않고 비교 가능한 옵션만 제시 · 투명성(Evidence Link)이 신뢰를 만든다는 원리 |
| **2. 전이 설계** | **전이 가설 (Hypothesis)** | 최적화 엔진(TMAP류)과 리밸런싱 트리거(핀트류)가 만들어낸 복잡한 계산 결과를 그대로 노출하면 사용자가 이해·신뢰하지 못해 이탈할 위험이 큼. 토스의 Decision UX 원칙(결론 우선·단계적 공개·Trade-off 명시)을 이식하면 다중목적 최적화 결과도 목적이 뚜렷한 카드로 압축 제시할 수 있어, 선택 피로 없이 실행률을 높일 수 있다는 가설 |
| | **적용 형태 (Adapted Feature)** | **3-Coverage 결과 카드 UI**: 첫 화면엔 안(혜택중심/월부담중심/간편중심)별로 핵심결과·필요한 변경·가장 큰 장점·가장 큰 Trade-off 4개 정보만 노출(Result First + Progressive Disclosure). 상세화면에서 구매건별 결제계획표(근거·기준일 포함, Evidence Link) 제공. 문구는 해요체·능동형으로 통일 |
| **3. 검증 & 리스크** | **핵심 검증 지표 (Success Metric)** | 첫 화면 체류시간/이탈률, 상세화면 진입률(근거 확인 의향), 3안 중 선택 분포, 문구 이해도(정성 인터뷰) |
| | **한계점 및 리스크 (Failure Mode)** | 과도한 단순화는 "왜 이런 결과가 나왔는지" 불신으로 이어질 수 있음(설명가능성 부족) · 3개 안 자체가 선택 피로(Scenario Overload) 유발 가능 · 해요체 톤이 금융 의사결정의 신중함과 맞지 않는다고 느끼는 사용자층 존재 가능 |
| | **보완 장치 (Mitigation)** | 기본 추천 1개 + 대안 2개로 위계를 둬 "고르기"보다 "동의/변경"의 프레임으로 전환 · 근거는 항상 1탭 안에서 접근 가능하게 유지(숨기지 않는 Progressive Disclosure) · 톤앤매너는 A/B 테스트로 검증 |

## 종합 인사이트

세 서비스(핀트·TMAP TMS·토스)는 벤치마킹 레이어가 겹치지 않으며, 뱅크샐러드까지 포함하면 4개 원리가 서로 다른 층위에서 결합된다.

| 레이어 | 원본 | 우리 서비스에 전이되는 원리 | 상태 |
| :--- | :--- | :--- | :--- |
| 동기 부여 | 뱅크샐러드 | 손실 프레이밍으로 지출 입력·비교 열람을 유도 | 채택 |
| 전환 판단 | 핀트 | 변화가 바꿀 가치가 있을 때만 단일 카드 교체를 트리거(비용-편익 게이팅, 정기 주기는 제외) | 채택·구체화 완료(§2) |
| 배분 계산 | TMAP TMS | 구매건×카드×시점×할부의 다대다 최적 배분 | **보류**(§3) — 원본-대상 구조 불일치 |
| 결과 전달 | 토스 | 복잡한 계산 결과를 결론 우선·단계적 공개로 압축 | 채택 |

TMS가 보류인 동안 MVP는 핀트 라인(§2)의 **단일 카드 교체 제안**으로 배분 역할을 대신한다 — 항목별로 가장 유리한 카드 1장을 추천할 뿐, 카드 수·월예산 같은 전역 제약을 동시에 최적화하지는 않는다. 뱅크샐러드 없이는 입력 동기가 없고, 핀트 없이는 매번 바꾸라고 해서 피로하며, 토스 없이는 계산 결과가 사용자에게 도달하지 못한다.
