시나리오 계산 원칙

총액에 일괄 ±20%를 적용하지 않습니다. 각 미래지출의 확정/추정 여부와 반복지출의 개인 변동성을 먼저 반영한 뒤 합산합니다. 확정 지출은 세 시나리오에서 그대로 유지됩니다.

Expected Spend = MyData 반복소비 Forecast + 사용자 미래지출 중앙추정치
Low / Base / High = 항목별 분포의 P25 / P50 / P75 합산 → 각 시나리오별 Optimizer 재실행

Prototype 예시

2,055만원적게 쓸 경우 · P25
2,300만원예상 지출 · P50 · Default
2,545만원많이 쓸 경우 · P75

금액이 달라지면 카드 수만 바뀌는 게 아니라 실적 충족, 혜택한도, 연회비, 기존 카드의 역할까지 전부 다시 계산됩니다.

02. Live Mobile Prototype

iPhone 17 계열 비율을 기준으로 만들되 문서 안에서는 330×690px로 축소해 한 화면에 프로토타입과 설명이 함께 보이도록 했습니다.

03. Full UX Blueprint

화면을 억지로 많이 나누지 않고, 사용자 행동과 시스템 상태를 구분했습니다. 결과 시나리오 선택 이후에만 상세화가 진행됩니다.

04. Product Logic & Guardrails

초기 MVP 문서에서 현재 제품 정의에도 유효한 요소를 반영했습니다.

INPUT

Future Spend

{ category, amount, date, certainty: confirmed|estimated, repeat: true|false }

일회성/반복지출, 금액의 확정·추정 여부를 보존합니다. 교통은 일반 소비 카테고리로 포함할 수 있습니다.

FORECAST

Scenario Engine

item distributions → P25 / P50 / P75 → category-level amounts

반복지출은 MyData 변동성, 미래 일회성 지출은 사용자 확실성을 반영합니다.

OPTIMIZER

Portfolio Rebuild

spendScenario × cardRules × hardConstraints → keep / remove / add / allocate

신규카드 수를 사전에 고정하지 않습니다. 유지·해지 후보·복수 추가가 모두 가능한 결과 공간입니다.

OUTPUT

Explainable Plan

{ cardRoles, assignments, netBenefit, performance, ruleBaseDate, uncertainty }

예상 순혜택과 실적 충족 가능성, 적용되지 않은 조건, 공식 출처 기준일을 함께 보여줍니다.

05. Exception States

계산을 억지로 완성하지 않는 상태를 별도로 정의합니다.

NO FUTURE SPEND

미래지출 없음

추천을 중단하고 MyData 반복소비만 볼지, 미래 계획을 추가할지 안내합니다.

CONSTRAINT CONFLICT

필수조건 충돌

반드시 유지할 카드와 해지 금지 조건 등이 조합을 막으면 어떤 조건이 충돌하는지 설명하고 조정으로 복귀합니다.

RULE UNKNOWN

확인 필요

혜택 적용 여부나 약관 데이터가 부족하면 임의 계산하지 않고 해당 카드/혜택을 `확인 필요`로 분류합니다.

STALE DATA

기준일 경과

카드 Rule 기준일이 오래됐으면 추천 정확도 경고를 표시하고 공식 상품정보 재확인을 요구합니다.
