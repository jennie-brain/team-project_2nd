## 0. 최종 판단

**차별화는 체인의 중간 두 단계에서 나온다.**

| | 체인 |
| --- | --- |
| 경쟁자(뱅크샐러드·토스·카카오페이) | 과거 소비 조달 → 단일 카드 매칭 → 결과 표시(발급 연계) · **3단계** |
| **CardFit** | 미래 의도 포착 → 시나리오 모델링 → **제약 최적화** → **결제수단 배분** → 카드사 신청 페이지 연결 · **5단계** |

**경쟁자 체인에 중간 두 단계(제약 최적화·결제수단 배분)가 아예 없다** 🔵. 마지막 단계(신청 페이지 연결)는 경쟁자도 하는 일이라 차별점이 아니다 — 차별점은 **그 단계에 도달하기 전에 조합 재배치·결제수단 배분을 거치느냐**다.

**두 번째 핵심 결정은 스코프 경계다.** 해지 상담·해지 신청 대행은 **어떤 형태로도 제공하지 않는다**. "이 카드를 해지하세요"라고 계산 결과를 제안하는 것과, 실제 해지 절차를 대신 처리·안내하는 것은 다른 일이며 후자는 카드사의 책임 영역이다. 이 경계가 [08](08_Value_Proposition.md)의 🔶 판정과 [09](09_PRD_Requirement_Trace.md)의 명시적 제외 항목을 만든 정의처다.

## 1. 상세표

### 1-1. 주요활동 (Primary Activities)

| # | 활동 | 핵심 결정 | 근거·등급 |
| :---: | --- | --- | :---: |
| 1 | **투입·조달 물류** | 원자재는 두 축이다 — 마이데이터 API의 **과거 소비 기록**(가맹점·업종·금액) + **보유카드 목록**, 그리고 사용자가 직접 입력하는 **미래 소비 변화값**(카테고리·금액·시점). MVP부터 마이데이터 연동을 포함하며, 직접 인가 또는 기존 인가 사업자 제휴로 접근권을 확보한다. 카드 혜택 Rule은 통합 API가 없어 **카드사별 공식 약관에서 직접 수집**한다 | 🔵 (→ [01](01_Five_Forces.md) F-01·F-05) |
| 2 | **운영·생산** | 과거 소비 + 미래 변화를 카드별 전월실적 구간·혜택한도·연회비 규칙에 대입해 예상 순혜택을 산출한다. **혜택 금액 계산은 결정론적 규칙 엔진, AI는 계산 근거를 사용자 언어로 설명하는 역할에 한정**한다 | 팀 결정 |
| 3 | **산출·배송 물류** | 계산으로 압축된 **하나의 최종 추천 조합**(예: "A·B 해지, C 유지, D 신규 추가") + 카드별 역할·배분금액 + 지금 그대로 두면 놓치는 금액 + 계산 근거 + **적용되지 않은 조건**. 신규 추가 카드에는 카드사 공식 신청 페이지 링크를 붙인다 | 팀 결정 |
| 4 | **마케팅 및 영업** | Beachhead = 혼인·이사 등 1~3개월 내 고액구매 예정 + 마이데이터 이용자. **초기 채택자는 혼인 세그먼트**, 유치 채널은 웨딩업체 제휴. Concierge Test로 조합안 선택률을 실측한다 | → [04](04_TAM_SAM_SOM_Segment_Map.md) |
| 5 | **서비스** | **계산 오류 신고·정정이 유일한 사후지원 활동**이다. 카드 신청·해지 실행은 대행하지 않는다 | 🔵 해지 마찰 민원 |

**활동별 개선 과제(🚀)**

| 활동 | 개선 과제 |
| --- | --- |
| 투입·조달 | 단일 채널(마이데이터 API)에 대체 경로가 없다 → **API 장애 시 "최근 확인된 데이터 기준" 경고**로 완화. 혜택 Rule **버전관리**(적용 시작일·종료일 기록)와 최신성 경고를 기술설계 원칙에 포함 |
| 운영·생산 | 전월실적 **1원 부족**, 월 한도 초과, 실적 충돌 등을 필수 경계값 테스트로 검증. 필수 데이터 누락 시 **추천 중단**, 데이터가 오래되면 경고 |
| 산출·물류 | 첫 화면에는 핵심 결과·필요한 변경·**순혜택(전환비용을 이미 반영한 숫자)**만. 세부 계산 과정은 눌러야 펼쳐지도록 단계적으로 숨긴다 |
| 마케팅 | 사람이 직접 응대하는 **Concierge Test**로 실제 수요를 먼저 확인 |
| 서비스 | 계산 오류율·불필요한 신규카드 추천 비율을 검증지표로 추적 |

### 1-2. 지원활동 (Support Activities)

| # | 활동 | 핵심 결정 |
| :---: | --- | --- |
| 1 | **기업 인프라** | 직접 인가 취득 **또는** 기존 인가 사업자 제휴 중 한 경로로 데이터 접근권 확보. 여신전문금융업법·개인정보보호법 전송요구권 확대·마이데이터 허가요건(자본금 5억원 등)을 전제로 사업계획 수립. **규제 리스크가 해소되기 전까지는 성장보다 리스크를 우선**한다 |
| 2 | **인적자원** | 금융(카드 약관·마이데이터 규제) + 데이터(혜택 Rule 파싱·버전관리) + 제품(계산 로직 설계) 역량의 결합 |
| 3 | **기술 개발** | **"AI가 혜택금액을 임의 계산하지 않는다"**는 원칙. 카드사별 혜택 Rule을 별도 레이어로 관리하고, 정책혜택(K-패스 등)과 카드사 자체 혜택을 분리. 경계값 자동 테스트 + 계산 과정·적용 규칙 로그 보존으로 **재현 가능성** 확보 |
| 4 | **조달·구매** | 마이데이터 표준 API(카드 업권 정보제공 API 규격) + 카드사별 공식 약관 데이터. 단일 채널이라 대체 공급자가 없어 **데이터 최신성 경고로 부분 완화**만 가능 |

### 1-3. 스코프 경계 — 이 프로젝트의 핵심 결정

| 하는 것 | 안 하는 것 |
| --- | --- |
| "이 카드를 해지하세요"라고 **계산 결과를 제안** | 실제 해지 절차를 **대신 처리·안내** |
| 신규 카드는 카드사 공식 신청 페이지로 **이동 링크 제공**(뱅크샐러드와 동일) | 신청서 작성·제출 **대행** |
| 포인트 소멸·자동납부 승계를 **"이 계산에 포함되지 않았습니다"로 공개** | 별도 "해지 안내" 활동 |

> 이동 링크만 연결하는 것은 "대행"이 아니다. 다만 **여신전문금융업법상 모집인 등록 대상 여부는 🟠 미확인**이다 → [10](10_Evidence_Inference_Assumption.md) U-05.
>
> 포인트 소멸·자동납부 승계 같은 부수 비용은 별도 "해지 안내" 활동이 아니라 **근거 공개 원칙의 일부**다 — 계산에 포함되지 않은 비용이 있으면 그렇게 밝혀 계산 정확성의 한계를 투명하게 드러낸다.

## 2. 산식·계산

정량 산식은 없다. 대신 **차별화 구간의 정의**가 이 파일의 계산에 해당한다.

```
차별화 구간 = (우리 체인의 단계 집합) − (경쟁자 체인의 단계 집합)
            = {제약 최적화, 결제수단 배분}

제약 최적화  : 사용자가 지정한 최대 카드 수 안에서 해지·유지·신규추가를 함께 계산해
               Net Benefit이 가장 큰 하나의 조합으로 압축
결제수단 배분 : 그 조합에서 어느 카드를 어느 카테고리에 얼마씩 쓸지 배정
```

**흐름 설계(운영·생산 단계의 순서)** — 확정본이 고정한 7단계다.

```
마이데이터 연동(과거 소비·보유카드 확인)
  → 미래 소비 변화 입력
  → 제약조건 입력(최대 카드 수 포함)
  → 시나리오 계산
  → 해지·유지·신규추가를 함께 계산해 Net Benefit이 가장 큰 하나의 조합으로 압축
  → 결제수단 배분
  → 근거 공개
```

**정보 계층화 순서(산출·배송 물류)** — `결론 → 핵심 변화 → Trade-off → 근거 → 상세 Rule`
